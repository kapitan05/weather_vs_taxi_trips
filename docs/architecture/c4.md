The system relies on two external data providers:

## Level 2 - Container

The Container level zooms into the system boundary to show the high-level deployable units (containers) and how they interact. The system uses a clear layered architecture.

* **Nginx Proxy**: A reverse proxy that serves the static frontend at the root path (`/`) and routes all API requests (`/api/*`) to the backend.
* **Dashboard App**: A Single-Page Application (HTML / JS / Chart.js) rendering time series, scatter plots, and bar charts based on fetched correlations.
* **REST API**: A backend application built with FastAPI. It exposes endpoints for fetching trips, weather, and correlation data, and auto-generates a Swagger UI.
* **PySpark ETL Batch Job**: A data processing script (Apache Spark, Python) that ingests raw taxi Parquet files and weather JSON into staging tables, then aggregates them into analytical models.
* **Data Warehouse**: A PostgreSQL database holding two schemas: `staging` (raw data overwritten on each run) and `analytics` (daily aggregates read by the API).

## Level 3 — Component

The Component level shows the internal building blocks of our two most complex containers: the REST API and the PySpark ETL process.

### 3.1 REST API Components

The REST API is structured to cleanly separate routing, business logic, and database access:

* **Application Core (`src/api/main.py`)**: Bootstraps the FastAPI application, registers CORS middleware, global exception handlers, and mounts static files.
* **DB Connection Pool (`src/api/db.py`)**: Manages a ThreadedConnectionPool for PostgreSQL. It exposes a `get_conn()` context manager used by all endpoints.
* **Models (`src/api/models.py`)**: Validates and serializes query results for Trips, Weather, and Correlation responses.
* **Routers (`src/api/routers/`)**: 
  * `trips.py`: Exposes `GET /api/trips/daily` endpoint with date filters.
  * `weather.py`: Exposes `GET /api/weather/daily` endpoint with date filters.
  * `correlation.py`: Exposes `GET /api/correlation/` endpoint joining trips and weather data.

### 3.2 PySpark ETL Components

The ETL pipeline is designed as a modular batch processing script:

* **ETL Orchestrator (`main.py`)**: Creates the Spark session and orchestrates the batch ingestion and transformation processes based on provided date arguments.
* **Logger (`src/ingest/logging_config.py`)**: Configures structured JSON logging for monitoring the ETL execution.
* **Taxi Ingestor (`src/ingest/taxi_ingest.py`)**: Downloads TLC Parquet files via Spark, cleans invalid rows (e.g., zero passengers or negative fare), and writes to the staging schema.
* **Weather Ingestor (`src/ingest/weather_ingest.py`)**: Fetches hourly weather data via the Open-Meteo API with exponential backoff and retry mechanisms, converting JSON responses to Spark DataFrames before saving to staging.
* **Transform Pipeline (`src/transform/pipeline.py`)**: Reads the staging tables, computes daily aggregates (averages, sums), and outputs clean, joined data into the analytics schema.

## Database Schema Design

The Database follows a standard Data Warehousing layout divided into raw staging data and clean analytics datasets.

```
staging
├── fact_trip         (Raw TLC columns: vendor_id, fare_amount, trip_distance, etc.)
└── fact_weather      (Raw Open-Meteo hourly rows: time, temperature_2m, precipitation)

analytics
├── daily_trips       (trip_date PK | trip_count | avg_fare | avg_distance | avg_passengers)
├── daily_weather     (weather_date PK | avg_temperature | total_precipitation | dominant_weathercode)
└── daily_correlation (record_date PK | all trip + weather columns joined on date)
```
